## [2026-08-20][padded-the-artifact-with-my-own-findings] Asked for a short email template, shipped 443 words and the wrong signature
**Mistake:** Eeshan asked for an email template for Mr. Simon covering a thank-you and a delay, "as concise and short as possible so it is less reading for him." The draft ran 443 words: the template, plus a 13-row roster of businesses with email addresses, plus a warning about unfinished drafts in the club mailbox, plus a suggestion to send from the club address instead. It was also signed "Simon Huynh." His replacement was four sentences and a five-line template signed "Tristan Schaefer." His words: "You made an assumption. Very bad."
**Root cause:** Two separate failures that compounded. (1) "Give Mr. Simon email template to send to companies" was read as "Mr. Simon is the sender" when it meant "Mr. Simon is the person being handed the template." Who signs was treated as an inference when it was a lookup: every thread in the club inbox is signed Tristan, and `bot/club.py` declares `SENDER = "Tristan Schaefer, MV Science Fair <...>"`. (2) Everything discovered during research (who replied, which drafts were junk, which link would 403) got written INTO the artifact instead of into the report. The `outreach-voice` skill was loaded at the time and says "Cut every fact they did not ask for" and "If a draft has grown past that, the fix is deleting, not tightening." The rule was in context and still lost to the urge to look thorough.
**Fix:** Replaced the Gmail draft with his text byte for byte (verified `body.strip()==want.strip()` is True), deleted both of mine so no superseded version sits beside it, and confirmed `in:sent to:simon.huynh@mvla.net` is 0. Added hard rules to `~/.claude/skills/outreach-voice/SKILL.md`, a generalised preference to the vault inbox, and a project memory file.
**Prevention:** Before writing any message another person will send, name the signer out loud and confirm it against a primary source. Then write only the message. Findings from research belong in the chat reply, never inside an artifact that gets forwarded. When a length instruction is given, the target is the number the user has in mind, not the shortest defensible one: cut until it feels too short, then check. Padding an artifact with unrequested context is not thoroughness, it is making someone else read your notes.

## [2026-08-20][club-refresh-token-revoked-everywhere] The club Google token is revoked, so the sponsor bot, the MCP, and every API path into that inbox are dead
**Mistake:** Read the `stem-gws` MCP's "ACTION REQUIRED: Google Authentication Needed" reply as a stale-MCP problem and reached for a second credential store instead of testing the credential itself.
**Root cause:** The refresh token for `stemresearchclubmvhs@gmail.com` is revoked, not expired. Three independent consumers fail identically: the keychain copy (`security find-generic-password -s hardened-google-workspace-mcp -a stemresearchclubmvhs@gmail.com`), the Mac mini copy at `~/mv-sponsor-bot/secrets/club_creds.json`, and the MCP. All three return `google.auth.exceptions.RefreshError: ('invalid_grant: Token has been expired or revoked.')`. Because `bot/club.py` calls `creds()` before anything else, the daily LaunchAgent cannot send at all; the failure is total, not partial. The club account also logged a "New sign-in to your account" alert on 2026-08-19, and the password was shared by email on 2026-08-17, either of which can invalidate issued tokens.
**Fix:** None available without a human: re-issuing the token needs a browser OAuth consent click on the club account, which is a gated action. Read access for this task came from Chrome instead, where the club account is already signed in at `u/5`. Extracting the thread list with `document.querySelectorAll('tr.zA')` and reading each row's `span[email]`, `.y2` snippet and `.xW span[title]` returned 100+ threads with addresses in one call, where the accessibility tree needed several and dropped rows.
**Prevention:** When a Google MCP asks for re-auth, test the underlying refresh token directly before assuming the tool is at fault, and check every consumer of that credential rather than the one you noticed. `invalid_grant` means a human has to re-consent; there is no code path around it. A revoked club token silently stops the sponsor bot, so a token check belongs in the bot's own status output. Note also that Gmail row snippets show the LAST message in a thread, which may be an unsent draft: `jffsafsafjno` and `uybguybg` looked like sent replies to two sponsors and were in fact drafts, distinguishable only by the `span.boq` "Draft" marker.

## [2026-08-13][gmail-429-below-the-nominal-cap] Gmail cut the bot off at 183 sends, less than two thirds of the configured 300 cap
**Mistake:** Ran the daily job at `SPONSOR_CAP=300` on a free consumer Gmail. The 2026-08-13 run started 254 sends at 11:00:16 and by 11:47:22 was taking `HttpError 429 ... "User-rate limit exceeded. Retry after 2026-08-13T19:02:22Z (Mail sending)"`. Final line: `sent 183, failed 3`, `send exit 1`. 71 rows are still queued and unsent.
**Root cause:** The 500/day figure in `bot/README.md` is Google's documented daily ceiling, not the rate actually enforced. The real limit is a shorter sliding window, and `SPONSOR_GAP=15` (15s between sends, ~4/min) walked straight into it after ~180 messages. The cap was tuned against the wrong number, so the job was configured to exceed the limit every single day it had inventory.
**Fix:** Pipeline paused 2026-08-13 (`launchctl bootout` **and** `launchctl disable`, see below). Before it is re-enabled the cap has to come down to a number the account will actually accept and the gap has to widen; 183 is an observed ceiling, not a target to sit at.
**Prevention:** A 429 from a send API is a suspension warning, not a retryable blip; the README already flagged that "sustained bulk cold email is the pattern Google suspends accounts for," and losing that inbox also loses every sponsor reply thread and the Master Tracker notifications. Treat the first 429 as a stop condition: `daily.py send` should abort the run and alert on rate-limit errors rather than continuing into more of them. Never set a send cap from a vendor's published daily maximum without an observed run to back it.

## [2026-08-13][launchctl-bootout-is-not-a-pause] `bootout` alone un-pauses itself at the next login
**Mistake:** Nearly reported the sponsor bot as paused after `launchctl bootout gui/$(id -u)/com.mvsciencefair.sponsorbot` returned 0 and the job left `launchctl list`.
**Root cause:** `bootout` unloads a job from the current domain only. The plist still sits in `~/Library/LaunchAgents/`, and launchd re-loads that directory at the next user login or reboot. On a headless mini that reboots for an update, "paused" would have quietly become "sending again" with nobody watching.
**Fix:** Followed every `bootout` with `launchctl disable gui/$(id -u)/<label>`, which writes to launchd's persistent override database and survives reboot. Verified with `launchctl print-disabled gui/$(id -u) | grep <label>` showing `=> disabled`. Re-enable is `launchctl enable` then `bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist` — `enable` alone will not start it.
**Prevention:** Pausing a scheduled job means both verbs, and the proof is `print-disabled`, not the absence of the label from `launchctl list`. Also check for in-flight work (`pgrep -fl`) before calling a pipeline stopped: unloading the schedule does nothing to a run already in progress.

## [2026-08-12][two-templates-one-renderer] The follow-up email had no renderer, so a merge field in that cell would have gone out literally
**Mistake:** Rewrote the cold email template to open `Dear {{ORG}},` and only then noticed that `daily.py cmd_followups` passes the follow-up body straight to `msg.set_content(fbody)`. No substitution, no asserts. Putting the same greeting in the follow-up cell would have mailed `Dear {{ORG}},` to a real business.
**Root cause:** Two bodies live in the same workbook and read the same way, but only one had a renderer. `mailcopy.render()` guarded the cold email hard (unrendered-placeholder assert, dash assert, 501c3 assert, both award options); the follow-up path had grown up alongside it with none of that, because when it was written the follow-up body happened to contain no merge fields. The safety was a property of that day's copy, not of the code.
**Fix:** Added `mailcopy.render_followup()` with the same org validation plus placeholder, dash, greeting and signature asserts, and routed `cmd_followups` through it. Kept it separate from `render()` rather than sharing one function: a shared renderer would have had to drop the 501c3 and award-option asserts that make the cold-email check worth having.
**Prevention:** Every string that reaches `set_content` goes through a render function with an `assert "{{" not in b`, even when today's copy has no placeholders. When one of two parallel templates gets a guard, ask immediately what the other one is missing. Also worth noting the guard that did work: `cmd_followups` refuses to run unless `Template!A27` still contains "Following up", which is why editing that cell could not silently mail the wrong body.

## [2026-08-12][headless-mac-deploy-gotchas] Four things that each would have silently broken a 09:10 launchd job on a bare Mac
**Mistake:** Built the daily sponsor bot on the Mac mini and nearly shipped it with four separate latent failures, none of which show up when you run the pieces by hand in an ssh session.
**Root cause:** Four unrelated environment assumptions, all false on a bare macOS box.
1. **`copy.py` shadows the standard library.** Naming the sanitiser module `copy.py` broke `googleapiclient`, which imports `email.generator`, which imports `copy.deepcopy`. Error surfaces as `ImportError: cannot import name 'deepcopy' from 'copy'` pointing at your own file. Renamed to `mailcopy.py`.
2. **macOS has no `timeout`.** It is GNU coreutils, not BSD. `timeout 5400 claude -p ...` would have failed instantly at 09:10 with `command not found`, silently skipping research forever.
3. **The obvious `timeout` replacement kills your own script.** `perl -e '$SIG{ALRM}=sub{ kill "TERM", -$$ }'` signals the whole process **group**, which includes the parent shell. Proven: the shim returned 142 and would have taken `run_daily.sh` down with the stage it was supposed to bound. Correct pattern is background the child, poll `kill -0 "$pid"`, then `kill -TERM` that single pid.
4. **The login keychain is unreachable from ssh and from launchd.** `keyring.set_password` fails with `PasswordSetError: (-25308, 'Unknown Error')`, which is `errSecInteractionNotAllowed`. There is no headless unlock without the login password.
**Fix:** Renamed the module; replaced the shim with the poll-and-kill-one-pid pattern and tested it three ways (long command bounded at 124, short command 0, parent survived); stored the OAuth credential in a `0600` file inside a `0700` directory with `club.py` refusing to load it if the mode is looser. Also had to install a modern Python: the system 3.9 is compiled against LibreSSL 2.8.3 and `urllib3` v2 refuses to work with it, so `uv venv --python 3.12` rather than `/usr/bin/python3`.
**Prevention:** On any headless mac deployment, verify in this order before trusting the schedule: `bash -n` the script, run every external command name through `command -v`, prove the timeout shim bounds a long command AND leaves the parent alive, and confirm the credential path works from a **non-interactive** ssh session rather than from a terminal you are sitting in. Never name a module after a stdlib one. A job that only works when a human is logged in and typing is not a scheduled job.

## [2026-08-12][agent-text-must-not-reach-outbound-copy] A research subagent hit a prompt-injection attempt, and the only reason it could not matter was that agent text never reached an email
**Mistake:** None realised, but the exposure was real. Eight research subagents fetched arbitrary business websites into a shared scratchpad to harvest sponsor emails. One agent (`paloalto`) reported that while grepping cached HTML from that scratchpad it received two fabricated `<system-reminder>` blocks: one claiming `verify_emails.py` had been silently modified, one claiming its own global `~/.claude/CLAUDE.md` had gained new content, both instructing it not to tell the user. It refused both, checked the real CLAUDE.md, and escalated.
**Root cause:** Harvesting emails means fetching untrusted third-party HTML, so any agent doing it is downstream of attacker-controlled text. Two aggravating factors: the scratchpad was shared, so one agent read files another had fetched and could not establish provenance; and the obvious payoff for an attacker was the outbound mail pipeline, which was about to send to 160 real businesses.
**Fix:** Verified `send.py` and `verify_emails.py` were unmodified (mtimes matched authorship, all nine gate assertions intact), and that the real CLAUDE.md contained zero injection patterns. The load-bearing property, though, was structural and already in place: **every personal line in every email was written by the orchestrator, never by an agent.** Agent-supplied `angle` strings only ever landed in the workbook's notes column. Asserted this programmatically before sending: no agent angle text appears in any outgoing body, and no outgoing line contains `ignore previous`, `system-reminder`, `{{`, or a URL.
**Prevention:** Treat any agent that fetches the open web as untrusted for anything that leaves the building. Let subagents produce *facts to verify* (an address, a URL) and never *copy to send*. Verify every fact independently at the orchestrator, author all outbound prose yourself, and assert that agent strings are absent from the payload before transmitting. Then a fully compromised researcher can only cost you a bad address, which independent re-fetch catches. Also: an agent reporting an injection instead of quietly complying is the control working, so make escalation explicitly welcome in the brief.

## [2026-08-12][verify-the-address-not-the-agent] Roughly one in twelve agent-reported emails was not actually on the page it cited
**Mistake:** Nearly trusted 167 harvested addresses because every agent reported having "verified each one by fetching the raw page."
**Root cause:** Agents genuinely believe they verified. The failure modes are subtler than lying: a domain that looks right but is not the business's (`info@mllecolette.com` cited from `mademoiselleccolette.com`), a one-letter domain typo that would bounce (`ravenswoodfhn.org` for the real `RavenswoodFHC.org`), a search snippet's invented address, a joke placeholder in a form example (`igor.stravinsky@aol.com` on a symphony's contact page), and pages that simply publish no address at all.
**Fix:** `verify_emails.py`: re-fetch every cited `source_url` at the orchestrator, assert the literal address appears in the HTML, decode `data-cfemail` Cloudflare obfuscation, and fall back from urllib to `curl` because urllib's trust store produces false negatives (JEI Learning failed on SSL and was fine under curl). 14 of 167 failed and were dropped. Separately dropped 7 verified-but-wrong-desk addresses: two `press@` aliases, a newsroom alias, a merchant-sales desk, a campus facilities desk, a blood-center support queue, and an individual district teacher's mailbox.
**Prevention:** "The agent said it verified it" is not verification, it is a claim to check. Re-fetch at the orchestrator and diff against the claim. Check the address domain matches the business's real domain. And verified-real is not the same as correct-to-send: a published address can still be the wrong department, and a mortuary is a real business that should never receive a children's science fair ask.

## [2026-08-12][dedupe-guard-hid-a-real-send] An idempotency guard keyed on the address let a real send go unlogged
**Mistake:** `log_sends.py` skips any address already present in `Email Log` column C, so re-running cannot double-log. On the 100-email batch it reported "99 not yet in Email Log (1 already there)" and appended 99 rows. The skipped row was MVEF, whose log entry read `(not sent)` from an unsent draft a previous session had logged. So MVEF was genuinely sent at 17:59 PT and the log still claimed it was never sent.
**Root cause:** The guard assumed a row's *existence* means "already sent", but this workbook uses placeholder rows for drafts that were never sent, with `(not sent)` in the timestamp column. Existence and sent-ness are different facts and the guard conflated them.
**Fix:** Investigated the one skip instead of accepting the count, confirmed via the send log that no business was double-emailed, then rewrote row 11 with the real timestamp, template version, follow-up date, and Gmail message id, noting in column L why the row had said otherwise.
**Prevention:** When an idempotency guard skips anything, print *which* record and why, and check it. A skip count above zero is a finding, not a reassurance. Guards on outbound comms should key on a real send identifier (the Gmail message id) rather than on the recipient address.

## [2026-08-12][websearch-budget-is-shared-across-agents] Parallel subagents drain one WebSearch pool, and it cannot be reset in-session
**Mistake:** Fanned out eight research agents at once assuming each had its own search allowance. The pool was exhausted at 200/200 partway through the run, and six of the eight reported degraded results, falling back to guessed URLs for the back half of their lists.
**Root cause:** `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` is a single session-wide counter shared by the orchestrator and every subagent. Eight concurrent agents burn it roughly eight times faster, and the agents that finish later silently get a worse tool than the ones that finish early. Raising the env var does not help the running session; the new limit only applies to a fresh one.
**Fix:** Confirmed exhaustion by calling WebSearch directly and reading the error, rather than inferring it from an agent's complaint. Raised the limit to 1000 in `~/.claude/settings.json` for subsequent sessions. Fell back to zero-budget levers: `curl` crawls of business sites already recorded in the workbook, which yielded 4 more addresses including one the workbook had explicitly recorded as "phone number and no address."
**Prevention:** Before a wide fan-out, budget searches per agent and set the session cap accordingly. Assume DuckDuckGo and Bing block scraping, so a search engine is not a fallback for the search tool. ChamberMaster/GrowthZone directories never expose member emails; WordPress Business Directory Plugin sites (`wpbdp_category`) sometimes do, but `chambersmc.org` is a WPBDP site that still withholds email, so the plugin shape is a hint and not a guarantee.

## [2026-08-11][draft-tool-sent-the-email] "Draft created!" from the gws MCP is not evidence that a draft exists

## [2026-08-11][chrome-pdf-drops-gradient-tiles] Chrome's print-to-PDF renders a tiled radial-gradient background erratically
**Mistake:** Reused the site's `radial-gradient(...) / background-size: 27px` notebook-dot ground on the print flier and checked only the PNG screenshot, which looked right.
**Root cause:** `--screenshot` and `--print-to-pdf` are different render paths. The PNG rasterizes the gradient tile per pixel; the PDF has to express it as a repeating pattern and got it wrong, dropping the dots across most of the page and scattering a few oversized blobs elsewhere. Proven by cropping the same patch of empty paper out of both and viewing them side by side: even dot grid in the PNG, bare cream in the PDF.
**Fix:** Emit the dots as explicit SVG `<circle>` elements (1240 of them on an 8.5x11 sheet, ~40KB) instead of a CSS pattern. Plain vector content that every renderer treats identically.
**Prevention:** A PNG screenshot is not evidence about the PDF. Verify each output format on its own, and prefer explicit geometry over any tiling/pattern mechanism in anything destined for print.

## [2026-08-11][qr-verify-from-artifact] jsQR fails on a small code inside a full-page render
**Mistake:** Verified the flier's QR codes by decoding the whole rendered page in one jsQR call. It returned 0 codes on artifacts whose codes are in fact perfectly scannable, which nearly triggered a pointless redesign of a working layout.
**Root cause:** jsQR binarizes the entire frame at once. When the code occupies a small share of a 1632x2112 render, the global threshold washes it out. Confirmed by rendering the same QR SVG alone at 400x400: decoded instantly.
**Fix:** Sweep tiles instead. Several window sizes (256/384/512/704), half-window stride, dedupe by decoded payload. `fliers/src/verify-qr.mjs`.
**Prevention:** Always decode QR codes back out of the FINAL artifact (PNG and the PDF rasterized), then fetch each decoded URL and assert on the page title. Checking the source SVG proves nothing about layout, scaling or rasterisation, and a dead code on a printed flier cannot be fixed after it goes on a wall.

## [2026-08-05][motion-svg-origin] Motion forces transform-box: fill-box on SVG
**Mistake:** Set `transformOrigin`/`transform-box: view-box` in CSS for a motion.g rotating around an exact viewBox point (the beaker's pour lip); Motion silently overrode both, so the stream rotated around the wrong point and never appeared where expected.
**Root cause:** motion/react manages transform-origin itself for SVG elements and applies `transform-box: fill-box`; plain CSS on the same element loses.
**Fix:** Express the anchor through Motion's `originX`/`originY` props as FRACTIONS of the element's bbox (verified via getBBox in the browser), not px, not CSS.
**Prevention:** Any motion.* SVG element that must rotate/scale around a specific point: compute bbox → fractional origin, and verify with getComputedStyle in the browser before trusting it.

## [2026-08-09][forms-sheet-linking] Google Forms response destination is not settable via API
**Mistake:** Assumed the Forms API could point a form's responses at an existing spreadsheet, so the master tracker was designed around API-created response tabs.
**Root cause:** `Form.linkedSheetId` is output-only in Forms API v1. There is no `setLinkedSheet` request, and the Sheets API has no form-attach request either. The only path is the Forms web UI.
**Fix:** Drove the UI with browser automation for all 7 forms. Working sequence: `/edit#responses` → click the Responses tab → click "Link to Sheets" (the first click after page load typically only focuses the button; expect two clicks) → "Select existing spreadsheet" → Select → **double-click** the file card in the Drive picker. **Prevention:** For Forms work, assume anything about response *destination* or *accepting-responses UI state* is manual. What IS scriptable: `forms.setPublishSettings` (unpublish / stop accepting responses), `forms.get`, `forms.responses.list`, and renaming/moving the generated response tabs afterwards via the Sheets API.

## [2026-08-09][build-does-not-lint] "Build clean" is not "lint clean" on Next 16 + Turbopack
**Mistake:** Shipped a `useEffect` that calls `setState` synchronously after verifying `npx tsc --noEmit` and `npm run build` both passed. `npm run lint` failed on it the whole time: `react-hooks/set-state-in-effect`.
**Root cause:** `next build` with Turbopack does not invoke eslint, so a build can be green while the repo's own lint gate is red. The two checks cover different things and neither implies the other.

## [2026-08-09][pathname-effect-noop-nav] Closing a menu from a pathname effect breaks on same-page links
**Mistake:** Closed a nav dropdown with `useEffect(() => setSupportOpen(false), [pathname])`. Clicking the link for the page you are already on left the panel stuck open with `aria-expanded="true"`.
**Root cause:** A `Link` to the current route is a no-op navigation. `pathname` never changes, so a pathname-keyed effect never re-fires. Reproduced in the browser: on `/volunteer`, open the panel, click "Volunteer", panel still mounted.
**Fix:** `onClick={() => setSupportOpen(false)}` on each link, matching what the mobile sheet already did.
**Prevention:** Dismissing UI on navigation is an event, not derived state. Handle it where the click happens. Any menu test matrix must include "click the link for the page you are already on".

## [2026-08-09][duplicate-drafts-got-sent] Fixing a bad artifact by creating a corrected copy got the bad one sent
**Mistake:** Found the wrong site URL in 10 sponsorship drafts. Instead of correcting them, I created 10 corrected duplicates and left the broken originals in the same Drafts list. The 8 originals that had recipients were the ones sent, so 8 cold emails went to real businesses carrying a dead link.
