## [2026-09-13][example-boards-contradicted-their-own-tables] A page teaching kids to match their claims to their data shipped two claims that did not
**Mistake:** `/example-boards` was built because a parent asked for sample boards and there were none. Its whole premise is that a conclusion has to follow from the board's own numbers, and two of the three worked boards broke that. The paper towel conclusion said Brand C "came third" per gram when the table on the same board reads A 4.1, C 5.3, B 5.8, so C came second and beat A. The bean plant conclusion said the maze stems "were the longest and the thinnest" when the day 20 table on the same board reads hole box 16.4 cm, maze 14.1 cm, open light 13.0 cm, which puts maze in the middle, and stem length is not measured anywhere on that board under either reading. A third board claimed a 200 cm spread when its own five spreads are 205, 195, 186, 210 and 175, and a line chart caption said "four plants per group" while the block beside it said one seed never sprouted so the maze group is three. All four were caught by the `code-reviewer` agent recomputing the tables, not by me.
**Root cause:** the table, the chart and the prose were written as three separate pieces of copy in one sitting, and the prose was written from what I intended the result to be rather than from the numbers I had just typed. Nothing re-derived a single figure. Prose that describes a dataset reads fluently whether or not it is true of that dataset, so there is no felt friction at the moment of writing it: 5.3 sits between 4.1 and 5.8 whichever ordinal you attach to it, and the sentence sounds equally finished either way.
**Fix:** all four corrected against their own tables, plus the `n=3` caveat added to both the chart caption and the table caption so a reader who stops at the chart is not given a sample size the board disowns. Then a throwaway script re-derived every claim on every board from that board's own figures, including `16.4/3.1 = 5.29`, the five longest-minus-shortest spreads, the peak row, and `210/544 = 0.386` for "more than a third". Printed OK or MISMATCH per claim.
**Prevention:** any artifact that carries both numbers and a sentence about those numbers gets the sentence re-derived from the numbers by something that computes, before it ships. That is a five line script, it costs a minute, and eyeballing does not substitute for it: I read these boards four times on screen at four viewport widths and saw none of the four errors, because I was checking that they looked like boards. Applies to family letters with measurements in them just as much as to a page.

## [2026-09-07][sheets-swallowed-a-phone-number-that-started-with-plus] A phone number written to the tracker vanished behind a "Successfully updated" message
**Mistake:** Wrote David Cho's phone `+1 (408) 442-1705` into `Mentor Offers!E8` in the same `C8:H8` call as his name, grade and subjects. The tool answered `Successfully updated range 'Mentor Offers'!C8:H8 ... Updated: 6 cells, 1 rows, 6 columns.` and then, four lines below that, `Detailed cell errors in range ''Mentor Offers'!C8:H8': - 'Mentor Offers'!E8: ERROR - Formula parse error.` Five cells landed, one did not. Reading only the first line would have left the mentor's phone number blank on the row while every surrounding cell looked right.
**Root cause:** `modify_sheet_values` defaults to `value_input_option="USER_ENTERED"`, which parses input exactly as if a human typed it into the cell. A leading `+` starts a formula in Google Sheets, the same as `=`, so `+1 (408) 442-1705` is read as an expression and fails to parse. Nothing about the write is malformed; the value is simply not text as far as Sheets is concerned. The existing phone on Tristan's row, `8312771154`, never hit this because it has no leading `+`.
**Fix:** Re-wrote the single cell with `value_input_option="RAW"`, which stores the string verbatim, and read `A3:Q10` back to confirm `+1 (408) 442-1705` is sitting in E8 as text.
**Prevention:** Any value that starts with `+`, `=`, `-`, `@` or `'` needs `RAW`, and phone numbers in international format are the common case. More generally: a Sheets write result is not binary. Read past the success line to the `Detailed cell errors` block on every write, because the summary counts the cells it attempted, not the cells it stored.

## [2026-08-26][oauth-recovery-deadends-on-its-own-port] The gws MCP could never recover a dead token, because it tried to bind a port its own server was holding
**Mistake:** Read "Cannot initiate OAuth flow - callback server unavailable (Port 8011 is already in use on localhost)" as a stale-process problem and went to Chrome for club inbox access. Eeshan: "You shouldn't be using claude in chrome for this you should be using the gws for each account." Chrome was the wrong tool; the right move was to fix the MCP.
**Root cause:** Two independent faults that compound. (1) Three of four accounts had revoked refresh tokens: `eeshankhandelwal123@gmail.com` (dead since 2026-08-08, eighteen days), `mvhsphysicsastroclub@gmail.com`, and `stemresearchclubmvhs@gmail.com`. Only the MVLA Workspace account `100035635@mvla.net` has never once failed; `mcp_server_debug.log` records RefreshErrors for the consumer accounts going back to 2026-03-08. (2) `auth/oauth_callback_server.py:154` tested callback availability by **binding** the configured port and returned a hard failure on `OSError`. In stdio mode the process holding that port is the account's own MCP server, which already serves `/oauth2callback` — verified by `curl localhost:{8001,8010,8011}/oauth2callback` returning **HTTP 400, not 404**, on all three. So the single condition that meant "the callback is ready" was the condition that aborted the flow. Every token expiry since March produced an unactionable error about a busy port instead of a consent URL.
**Fix:** Patched `MinimalOAuthServer.start()` to probe the endpoint instead of the socket: 404 means a foreign listener and the failure is real, any other response means reuse it (`hardened-google-workspace-mcp` commit 892deff). Verified 6/6 against the live servers and a synthetic 404 listener; `start()` on port 8011 now returns `(True, "")` where it returned the error. Added `~/.local/bin/gws-health` (refreshes every stored account, verifies the token resolves to the account it is filed under, exits 1 with a per-account fix command) and `~/.local/bin/gws-reauth` (ephemeral loopback port, allowed because the client is a desktop app with an `http://localhost` redirect; refuses to store if the approved identity differs from the requested one; mirrors the credential into `~/mv-sponsor-bot/secrets/club_creds.json` at 0600 so a re-auth cannot fix the MCP while leaving the bot on a dead token). Wired `gws-health --quiet` into the global SessionStart hook, silent unless something is broken.
**Root cause, second half (verified 2026-08-26 against Google's docs):** the tokens are not dying at random. `https://developers.google.com/identity/protocols/oauth2` states: "A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of 'Testing' is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile." ## [2026-08-12][headless-mac-deploy-gotchas] Four things that each would have silently broken a 09:10 launchd job on a bare Mac

## [2026-09-17][launchagent-usr-bin-python] A LaunchAgent pointed at /usr/bin/python3 dies on the Xcode licence
**Mistake:** The one-shot agent `com.mvsciencefair.hadiya-deadline` was installed with `/usr/bin/python3` as its interpreter. It loaded cleanly, `launchctl print` reported `state = not running, runs = 0`, and everything looked correct. It would have produced nothing at fire time.

**Root cause:** `/usr/bin/python3` on this Mac is the Xcode command line tools shim. Invoking it returns `You have not agreed to the Xcode license agreements` on stderr and exits non-zero, before a single line of the script runs. This is the same shim behaviour recorded for `git` in the `git-needs-developer-dir` memory. Nothing in `launchctl bootstrap` or `launchctl print` surfaces it, because the failure happens inside the child process at fire time, and a job that has never fired reports the same `runs = 0` as a healthy one.

**Fix:** Point the plist at `/opt/homebrew/bin/python3`, which is the ARM-native interpreter and has no shim. Verified by running the script under a stripped environment that imitates launchd, `env -i PATH=/usr/bin:/bin LANG=en_US.UTF-8 HOME=/Users/Eeshan`, which reproduced the licence error with the system python and ran clean with the homebrew one.

**Prevention:** Never write `/usr/bin/python3` into a plist. Before trusting any new LaunchAgent, run its exact ProgramArguments under `env -i` with launchd's own PATH (`/usr/bin:/bin:/usr/sbin:/sbin`) rather than from an interactive shell, where PATH, the Homebrew prefix and a warmed-up environment all hide the problem. `launchctl bootstrap` succeeding proves the plist parses, nothing more.
